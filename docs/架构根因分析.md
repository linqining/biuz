## 1. 裁决：方向正确，全称不成立

| 统计口径 | 甲∪乙占比（甲=协议消息形状/信封错误；乙=架构性寻址/时序/生命周期） | 其余分布 |
|---|---|---|
| 会话库 50 主会话，去重约 50 个问题 | **约 55%（28 条）** | 丙（客户端工程）约 1/3；丁（工具链/环境）约 12%；戊（服务端/中继）约 8% |
| docs 58 条事故 | 甲约 38 条、乙约 22 条（重叠约 6），合计**约 6 成事件** | 丙约 26 条；丁约 7 条；戊约 8 条 |

- **支持面（判断的正确部分）**：全部 P0 级核心事故——createSession 对真实桌面静默全败（信封缺 sessionId 键）、「手机端没有回复」（订阅 workspace 寻址错 + 桥重开未重握手）、`/plan` 被拒 CAS（快照帧 handler 晚注册丢 revision）、附件四方法全链必坏（形状抄读侧）、web 一致性审查 33 条中的形状族（setAssistantFeedback 词表、resolveInteraction 三族、attachmentChunkV4 键名）——**无一例外落在甲/乙簇**。用户对「协议层故障主导」的直觉是准的。
- **反例面（全称不成立的部分）**：约四成问题与「架构→消息错误」无因果关系：
  - **丙=客户端工程**（约 1/4）：静默吞错/假成功（`try?`/`_ =`/UUID 兜底掩盖拒收/「任务已发送」不判 status）、SwiftUI a11y 四坑、sheet dismiss 先于 onConfirm、iOS26 键盘、面板 modifier 自伤、mock 数据源不重绑——形状全对也会坏；
  - **丁=工具链/环境**（约 1/8）：`xcodebuild|tail` 假绿、test-without-building 缺 `-derivedDataPath` 假红、PTY 池耗尽、Localizable 误 checkout、E2E 替身不校载荷形状；
  - **戊=服务端/中继行为**（约 1/10）：单连接槽 + 真机 -1001、REST bootstrap 对移动 sid 404、usage 并发拒绝、deleteSession 语义、桌面同 traceId 双 workspace 幽灵行、provider 抖动——消息再对也无效。

**精确表述（取代全称判断）**：约半数问题的**近因**是消息形状错误，**远因**是「上游无 API 文档、源码即唯一权威，而移动端早期未按参考客户端取证」；另约四分之一是寻址/时序/生命周期类同步问题（**不经形状错误直接致故障**）；再约四分之一与协议无关。且丙（吞错）是把甲/乙错误**放大成「无反馈」体验的独立放大器**，丁（测试基建不校形状）是让甲/乙错误**不被发现的独立放大器**——治理必须三线并行，单归因「架构」会漏治后两条线。

## 2. 上游架构不变量清单（消息为什么容易发错）【实证·上游仓】

## 3. 官方客户端为什么不踩坑（移动端应镜像的架构保障）【实证·上游仓】

官方 web/host 双端把形状错误**前移到构造期**，靠的是五件套：

1. **信封单点 builder ×2**：renderer 侧 `ui/src/v4/commandFactory.ts:51-70`（CAS/row-target 缺字段**构造时即抛**、clientId localStorage 持久化）、host 侧 `services/src/zcode-agent/zcodeV4HostCommand.ts:57-76`（两套不合并仅因包依赖方向 `:1-5`）。**业务代码从不手拼信封**。
2. **构造与校验同源**：客户端与服务端 import 同一个 zod schema 包（`@zcode/shared/zcode-protocol-v4`），`parseCommandEnvelope` 收口信封+payload 联合校验（`command.ts:340`）。
3. **可信字段服务端强制注入**：`withTrustedConnection` 显式删除可伪造的 `connectionId/clientMode/workflowRunDeltas` 再盖真值（`zcodeAgentConnectionScope.ts:94-105`）——客户端「选不了」也「伪造不了」。
4. **快照帧 staging barrier**：host 侧 pending ownership staging 缓冲先到的帧（`zcodeAgentConnectionScope.ts:415-478`，超限报 `initialFrameStagingOverflow`），参考客户端 `ackActivationBarrier` 同构（`ui/src/v4/ackActivationBarrier.ts:34-64`）。
5. **stale 自愈内建**：`sendHostCasCommandV4` 以 `revisionAtDecision` 探测-收敛循环（`zcodeV4HostCommand.ts:122-158`），业务层拿到的已是终态。

**上游无人类可读协议文档**：README/DESIGN.md 均无协议参考；schema 文件头自注「数据模型草稿（未冻结，定型以黄金测试为准）」（`core.ts:1`），行为规范靠 golden test + `packages/formal-proof/`（状态空间枚举器）背书；云中继服务端（zcode.z.ai/remote/v4）不在开源仓内。**源码即唯一权威**——「bundle 逆向 + 上游仓取证」双保险路线与该现实一致（AGENTS §5-11/§5-12）。

**推论**：移动端甲/乙类 bug 不是「桌面架构有缺陷」，而是「**客户端没有继承官方客户端的架构保障**」。§5 工程纪律第 2/3/5/6 条（统一 sendCommand 出口、handler 先注册、唯一 call 出口、订阅兜底链）正是对上表五件套的 Swift 镜像，落地后同类事故确实被压制（v1.21 后新增问题已多为丙类边缘）。

## 4. 四大静默陷阱（最危险：无错误码，表象全是「点了没反应/没有回复」）

1. **payload 未知键静默剥离**（A4）：命令被接受但语义已变。上游先例：`planEnabled` 被老 CLI 剥掉致 yolo+Plan 漂移成完全访问执行，官方只能客户端防御性剥键（`ui/src/v4/agentConversationTransport.ts:355-362`）。移动端对应风险：payload 键名拼错 = 命令成功但行为不达。
2. **桥重开后命令面无握手闸**（A6）：发送全成功、读面全线 handshakeRequired——v1.17「能发送、收不到」80 秒风暴的形态。
3. **订阅寻址错 workspace**（A7）：历史快照可读（全局 db 冷恢复）、运行中增量永不抵达，无任何错误码——v1.17「手机端没有回复」根因。
4. **帧 handler 晚注册/无屏障**（A8）：纯丢帧——v1.21「/plan 被拒 CAS」（快照帧先于回执抵达，revision/logEpoch 丢）根因。

这四个陷阱与客户端吞错类 bug（丙）**症状完全相同**（无反馈），历史上多次误判归因。

> **排查口诀：「没反应」先分诊**——发送面查 ACK status 词表（A13，非 accepted 看 reasonCode）；读面查握手（A6）/寻址（A7）/帧序（A8）；三条都正常才归客户端工程（丙）。

## 7. 防错总纲（新接口/新命令 checklist）

1. **形状**：先取证（上游仓 `rg` ＞ bundle 逆向 ＞ 真机探针）；payload 键名禁止推测——A4 的剥离是静默的，错了不报错。
2. **信封**：走 `sendCommand` 统一出口；CAS 类查 A3 权威词表 + `ensureStateRevision` 前置 + stale 收敛重试；重试复用 commandId（A12）；写级命令禁自动重试。
3. **寻址**：会话域读写/订阅/退订/resync/rowsRange/readSession/附件族一律 `workspaceTarget(for:)`（A7）；resync 必带 workspace 信封（notOwned）。
4. **时序**：帧 handler 先于 subscribe 注册（A8）；桥(重)开重握手单点（A6）；订阅回执无 subscriptionId = 错误路径（自愈链命脉，勿静默成功）。
5. **状态**：键级整替（A10）；epoch 不符整批作废（A9）；contentRejected 走终态不重试（A14）。
6. **反馈**：ACK 按 A13 六态词表判定，非 accepted/duplicate/noop 必上屏 reasonCode + message 原文（RPCError.message，非 localizedDescription）；读面 last-good + 失败文案三态。
7. **排查**：「没反应」按 §4 分诊口诀先分诊，再归因。

## 8. 元结论

「架构→消息错误」是本项目最大 bug 簇（约 5–6 成）且方向正确，但治理答案不是「修桌面架构」（改不了），而是三线并行：**镜像官方客户端的架构保障**（§3 五件套的 Swift 对应物——统一出口/同源校验/屏障/自愈，已在 AGENTS §5 落地并见效）、**取证纪律**（源码即唯一权威，§5-11/§5-12）、**禁吞错**（把静默陷阱显性化，§5-12）。工具链与测试基建（替身校形状、构建判定纪律）是独立放大器，需独立治理（§5-1/§5-16）。三者缺一，甲/乙类错误要么发生、要么发生而不被发现、要么被发现而无反馈。
