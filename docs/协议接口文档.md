## 1. 文档定位与证据等级

协议面标识（频道名、clientId、URL scheme 等）必须与服务端/对端注册值**逐字一致**，改任一处即断连。协议类型定义在服务端处于草稿态（core.ts「未冻结」声明），因此客户端实现一律**宽容解析**：单字段解析失败不丢弃整帧。

**证据等级标注约定**（全文适用）：

| 标记 | 含义 | 可信度 |
|---|---|---|
| 【实证】 | 真机 + 真实网关/桌面端联调实测（含错误码回执取证） | 最高，可直接依赖 |
| 【移植】 | 从上游开源仓库克隆件逐行移植/精读得出（标注 `file:line`） | 高，字段名以源码为准 |
| 【移植·bundle 逆向】 | 【移植】子类：证据出自 web bundle（`/tmp/webshell2.js`，/remote/v4 页面）的 zod schema 与实调用点逆向。bundle 为单行压缩无行号，引用以「检索式」固化（如 `rg -o '.{80}generateCommitMessage.{260}' /tmp/webshell2.js`） | 高（wire 键名/值域以 bundle 为准）；**这是形状类事实的当前唯一权威准绳**（官方无 API 文档，上游克隆件已失） |
| 【宽容】 | 未逐字段取证，客户端按多形态兼容解析；字段名可能不准 | 低，改字段前先取证 |

## 2. 总览：两条传输链路

同一个 RPC 命令面经 clientMode 分两条链路【移植 http.ts:321-346】：

| | 局域网直连 | 云端中继（remote/v4） |
|---|---|---|
| 入口 | `GET /ws?token=…` | `wss://zcode.z.ai/remote/v4?sid=…&hash=…&t=…&mid=…&name=…` |
| clientMode | `web-remote-replayable`（手机/恢复链路） | 桌面桥内同样对齐 `web-remote-replayable` 语义 |
| 帧承载 | WS 二进制帧（13 字节头协议帧） | WS JSON 文本帧（`rpc-frame`，内嵌分片+base64） |
| 服务发现 | `GET /api/server-info`（HTTP 探测） | 无（跳过，配对链接即凭据） |
| 握手顺序 | 先订阅帧流、后 v4 握手（server 无握手闸） | **先 v4 握手、后订阅**（桌面桥有 `handshakeRequired` 闸，探针实测：握手前订阅报 `fault.connection.handshakeRequired`）【实证】 |
| 实现类 | `ChannelClient` | `RelayTransport` + `RelayChannelClient` |

两条链路在建连后**共用同一套** RPC 门面（`ZCodeServerConnection.call/listen`）、帧路由与只读拦截（`ReadOnlyGate`），上层 Store 无感知差异。

> **桌面专用链路**（移动端不使用）：`GET /ws/host`（clientMode=desktop-continuous），需 `POST /api/rpc-host-capability` 发放一次性 capability【移植 http.ts:341-346】。仅作认知记录。

## 3. 传输层协议

### 3.1 服务发现：`GET /api/server-info?token=…` 【实证】

局域网直连第一步。超时 3s，超时自动重试 1 次（1s 退避）。实现：`ZCodeServerConnection.swift:85-140`。

**请求参数**（query）：

| 参数 | 类型 | 意义 |
|---|---|---|
| `token` | string | 访问令牌；桌面端 `--no-token` 启动时不携带（免鉴权口径） |

**回执**（`ServerRemoteInfo`，解析 `ZCodeServerConnection.swift:22-46`）：

| 字段 | 类型 | 意义 |
|---|---|---|
| `serverId` | string（必填） | 服务实例 id |
| `name` | string? | 显示名 |
| `version` | string（必填） | 桌面端版本 |
| `protocolVersion` | int | **必须为 1**（SERVER_REMOTE_PROTOCOL_VERSION），否则报「协议版本不匹配」 |
| `authRequired` | bool | 是否要求令牌 |
| `workspaces` | array | 工作区列表，每项 `{path, label?, workspaceIdentity?}`；**空列表 = 连接失败**（emptyWorkspaces）。移动端默认取 `workspaces[0]` |
| `capabilities` | object | `{能力名: bool}` 键集，chips 展示用 |

> `workspace.workspaceIdentity`：桌面端代理派生 `workspaceKey = identity || path`；v4 会话域 RPC 的 workspace 信封需要它（见 §7）。缺失时可省略。

### 3.2 WS 升级：`GET /ws?token=…` 【实证】

5s 超时。升级成功后**服务端立即推送 Initialize 帧**（channel 层，见 §4），客户端等待它才算通道就绪（`ChannelClient.connect`，`ChannelClient.swift:143-175`）。token 为空时允许无 token 段（免鉴权）。

### 3.3 云端中继链路 【实证】（`docs/relay-handoff.md`）

配对链接形态：

```
https://zcode.z.ai/remote/v4?sid=<会话凭据>&hash=<URL编码base64>&t=<生成时间戳ms>&mid=<机器id>&name=<机器名>
```

- `sid` + `hash` 是口令级凭据（重新生成即旧凭据失效，为唯一已知撤销路径）；`t` 可能过期。
- 连接步骤（`ZCodeServerConnection.connectRelay`，`ZCodeServerConnection.swift:449-537`）：直连 WS（跳过 server-info）→ auth 握手（`pair_status=matched`）→ bootstrap → workspace-bridge-open → 桥内 Initialize → **桥内 v4 握手** → 订阅帧流。
- 桥回执汇总 `summary` 携带 `workspacePath`（成为 Store 装配的 workspace）、`sessionCount`、`desktopAppVersion`、`bridgeKind`。
- 桥内 v4 握手失败**降级继续**（旧版本桌面缺命令时不阻断）【实证】。
- 中继传输层瞬断（Reconnecting）会打断在途 RPC：移动端对「加载更早消息」「附件分块读」加了首败 1.2s 退避重试一次的兜底【实证】。

**中继 rpc-frame 帧格式**（JSON 文本帧，`.strict` schema 不得多带字段，`RelayFrameCodec.swift:1-30`）【移植 bundle 逆向】：

```
rpc-frame      = {zcode_type:"rpc-frame", bridgeSessionId, bridgeGeneration?, recoveryId?,
                  seq, messageSeq, fragmentIndex, fragmentCount, messageBytes,
                  checksum:{algorithm:"crc32", value:<hex8>}, dataBase64}
rpc-frame-ack  = {zcode_type:"rpc-frame-ack", bridgeSessionId, bridgeGeneration?, recoveryId?, ackMessageSeq}
```

| 字段 | 意义 |
|---|---|
| `seq` | 物理帧序号（每片 +1） |
| `messageSeq` | 逻辑消息序号（每条 RPC 消息 +1） |
| `fragmentIndex/fragmentCount` | 分片位次/总数（≤64 片） |
| `messageBytes` | 逻辑消息总字节数 |
| `checksum` | crc32 反射 0xEDB88320，hex8（与 §6 校验同参） |
| `dataBase64` | 分片载荷（带 padding 标准_base64） |

约束：单片信封 ≤ 1MB（`maxPhysicalFrameBytes`）、逻辑消息 ≤ 16MB、≤64 片、重组超时 30s。载荷内容 = `serialize(header)+serialize(body)`（与局域网相同，**无 13 字节头**）。

## 4. RPC 帧协议（channel 层）

移植自 `packages/rpc/src/protocol.ts` + `serialization.ts` + `channelClient.ts`。实现：`ChannelClient.swift` + `RPCSerialization.swift`。

### 4.1 协议帧（仅局域网二进制链路）

一条 WS 二进制消息 = 一个协议帧，**无需处理粘包**【移植 websocket.ts】：

```
[ type:1字节 ][ id:4字节BE ][ ack:4字节BE ][ length:4字节BE ][ payload:length字节 ]
```

`type`（`ProtocolMessageType`）：

| 值 | 名称 | 移动端处理 |
|---|---|---|
| 1 | regular | 业务帧（唯一消费的类型） |
| 3 / 9 | ack / keepAlive | 丢弃 |
| 其余（control/disconnect/replayRequest/pause/resume） | | 当前不实现，丢弃 |

### 4.2 值序列化（`RPCSerialization.swift`，serialization.ts 逐行移植）

每个值 = 1 字节类型标签 + 载荷：

| 标签 | 类型 | 载荷编码 |
|---|---|---|
| 0 | undefined | 无载荷 |
| 1 | string | VQL(字节长) + UTF-8 字节 |
| 2 | buffer | VQL(长) + 原始字节 |
| 3 | vsbuffer | VQL(长) + 原始字节 |
| 4 | array | VQL(元素数) + 逐元素递归 |
| 5 | object | **JSON 字符串**（VQL(字节长) + UTF-8；RPC 参数主体即此形态） |
| 6 | int | VQL(32 位值按无符号展开；负数按二补数) |

**VQL（Variable-Length Quantity）**：7 bit 数据 + 最高位续传标记，低位组在前。`RPCSerialization.swift:236-263`。

Object 内嵌二进制的标记约定：TS 端把 Uint8Array 编码为 `{__zcode_rpc_nested_uint8array_v1: true, base64: "…"}`；移动端当前业务面不消费嵌套二进制，解析后保持标记对象原样【移植 serialization.ts:136,220-250】。

### 4.3 请求/响应类型（channels.shared.ts）

**请求**（header = 序列化后的数组，body = 序列化后的参数值；两段拼接为 payload）：

| type | 名称 | header 形状 | 意义 |
|---|---|---|---|
| 100 | promise | `[100, id, channel, command]` | 一次 RPC 调用，等单一响应 |
| 101 | promiseCancel | `[101, id]` | 取消在途调用（移动端未使用） |
| 102 | eventListen | `[102, id, channel, event]` | 订阅事件，服务端按原 id 持续 eventFire |
| 103 | eventDispose | `[103, id]` | 退订（`EventSubscription.cancel()` 自动发） |

**响应**：

| type | 名称 | 意义 |
|---|---|---|
| 200 | initialize | 连接建立即推，通道就绪信号 |
| 201 | promiseSuccess | `[201, id]` + 结果值 |
| 202 | promiseError | `[202, id]` + 错误对象 `{message, name}` |
| 203 | promiseErrorObj | 同上，detail 保留原始错误对象 |
| 204 | eventFire | `[204, id]` + 事件载荷 |

- `id`：客户端单调自增（0 起）。
- 超时：客户端侧看门狗（默认 30s，可按调用指定），超时抛 `RPCError(name:"TimeoutError")`；响应/超时两路竞争保证恰好 resume 一次【移植 channelClient.ts:225-231】。
- 错误对象口径：`{message: string, name: string}`；`name` 参与程序化判断（如 `TimeoutError`、`V4SubscribeSessionUnavailableError`）。

## 5. v4 握手

v4 会话协议的握手两步，均在 `zcode-agent` 频道，无业务副作用【移植 zcodeAgentService.ts:4901-4926】。实现：`ZCodeServerConnection.swift:378-419`。

### 5.1 `helloConversationV4`

**参数**：undefined（无参）。
**回执**（`V4HelloMessage`）：

| 字段 | 类型 | 意义 |
|---|---|---|
| `protocolVersion` | int | **必须为 3**（V4_WIRE_PROTOCOL_VERSION），否则连接失败 |
| `connectionId` | string | 服务端连接 id |
| `clientMode` | string | 必须为 `web-remote-replayable`，否则 handshakeFailed |
| `deliveryProfile` | string | 投递档位（强制匹配 clientMode【移植 transport.ts:56】） |
| `serverTime` | string? | 服务端时间 |
| `capabilities` | `{string: bool}` | 服务端能力集（hello 能力集因 clientMode 而异【移植 zcodeAgentConnectionScope.ts:206-228】）。含 `workspaceHookReview: bool?` 标志（bundle `fle=Ta({...workspaceHookReview:Vo().optional()...})` 取证，2026-10-06） |
| `auth.userId` | string? | 登录用户 id |

### 5.2 `initializeConversationV4`（clientHello）

**参数**（移动端构造，`ZCodeServerConnection.swift:397-403`）：

| 字段 | 值 | 意义 |
|---|---|---|
| `kind` | `"clientHello"` | 帧类型标识 |
| `protocolVersion` | `3` | 回应 hello 的 wire 版本 |
| `clientId` | `"zcode-mobile-" + UUID 前 8 位` | **连接级唯一标识**；后续所有 `sendConversationCommandV4` 信封的 `envelope.clientId` 必须与它逐字相等，否则 `fault.command.clientMismatch`【实证】 |
| `clientKind` | `"mobileApp"` | 客户端种类（transport.ts:73 预留值）【移植】 |
| `appVersion` | string | App 版本号 |

> **capabilities 单向宣告规则**【移植 transport.ts:53-86 `.strict()`】：clientHello **不携带** capabilities 键 = 旧客户端语义，严格满足「客户端不得宣告 Host 未宣告的能力」——多带键会整条解析失败。

**回执**：无业务字段（成功即完成握手）。

### 5.3 桥(重)开握手纪律（中继）【实证·真机 2026-10-07 + 上游仓】

- **每次 workspace 桥建立/重建（首连 openBridge / 断线恢复重建 / degraded 快速重建 / 工作区切换）桌面侧都是全新 scoped facade**，`handshakeComplete` 为 facade 实例态、仅 `initializeConversationV4(clientHello)` 置真【实证·上游仓 `zcodeAgentConnectionScope.ts`】——**桥重开后必须重做 hello → clientHello**，否则 assertReady 类调用（`subscribe*` / `readSession` / `conversationRowsRangeV4` 等）全部 `fault.connection.handshakeRequired`。
- **真机实证（2026-10-07 18:33–18:34）**：桥重开后无重握手 + 握手失败「降级继续」叠加，手机端 80 秒内 subscribe/订阅索引/readSession/rowsRange 全线 handshakeRequired 风暴，直到下一轮整连接重建恰好完成握手才自愈。
- **移动端口径（v1.17）**：握手单点接管于 `RelayChannelClient.openBridge`（`waitForInitialize` 之后、`resendActiveEventListeners` 之前，经 `onBridgeOpened` 钩子回调 `ZCodeServerConnection.performRelayV4Handshake`）；握手瞬态失败退避 1.2s 重试一次，仍失败维持旧桌面降级放行（旧桌面无握手闸不受影响）。
- §6 未决事项⑦（workspace-reconnect 桥重开后是否要求重握手）就此闭合：**要求**。

## 6. topic 帧协议（快照/增量流）

移植自 `packages/shared/src/zcode-protocol-v4/{wire,wire-assembler,transport}.ts`。实现：`V4Wire.swift`。

### 6.1 订阅模型

- **订阅方法**（promise 面）：`subscribeConversationV4` / `subscribeSessionsIndexV4` / `subscribeWorkspaceConfigV4`，回执携带 `subscriptionId`。
- **下行帧流**（event 面）：三个 dynamic 事件共用 workspace 级通知面，按 `topic` 前缀分流：

| 事件（zcode-agent 频道） | 承载 topic 前缀 | 参数 |
|---|---|---|
| `onDynamicConversationFrame` | `conversation/<sessionId>` | `{workspacePath}` |
| `onDynamicSessionsIndexFrame` | `sessions-index/<workspacePath>` | `{workspacePath}` |
| `onDynamicWorkspaceConfigFrame` | `workspace-config/<workspacePath>` | `{workspacePath}` |

- **注册时序**：帧 handler 必须先于 subscribe 调用注册——中继桥的快照帧会在 subscribe 回执前到达，晚注册会静默丢帧（曾致「连接成功但会话列表恒为空」，e2e 实证）【实证】。
- **runtimePolicy**：`subscribeWorkspaceConfigV4` 与 `readSession` 携带 `"existing-only"` = 被动观察者，禁止为订阅拉起 Agent 进程【移植 zcodeAgent.ts:527-529 注释口径】。conversation 订阅本身有 spawn CLI 进程的副作用（如实标注【移植 §7.2】）。

### 6.2 物理帧信封（TopicWireFrame.Envelope）

eventFire 载荷形状：

| 字段 | 类型 | 意义 |
|---|---|---|
| `wireVersion` | int | wire 版本（必填） |
| `kind` | `"complete"` \| `"fragment"` | 完整帧直过 / 需重组 |
| `deliveryKind` | string | 投递档位 |
| `logicalFrameId` | string | 逻辑帧 id（分片重组键） |
| `logicalFrameOrdinal` | int | 逻辑帧序 |
| `topic` | string | 所属 topic |
| `subscriptionId` | string | 订阅回执 id |

### 6.4 水位与 resync 自愈【实证】

- **水位**：`(logEpoch, seq)`。`logEpoch` 仅快照携带（缺席沿用旧值）；`seq` 取每帧 `toSeq`。
- **resync 调用**：`resyncConversationV4` / `resyncSessionsIndexV4` / `resyncWorkspaceConfigV4`，参数统一：

```json
{ "subscriptionId": "<订阅回执>", "base": {"logEpoch": "<epoch>", "seq": 123} }
```

`base` 传 `null` = 无水位，服务端重发全量快照（幂等无害，多场景兜底都用它）。
- 触发点：① assembler dropped；② 快照 `state.workflowRuns` 间歇缺席的一次性自愈（2.5s 后 nudge UI 刷新）；③ amend 工作流设置后的主动全量 resync（5s 节流）。
- 订阅失败兜底链：`subscribeConversationV4` 失败 → `readSession(runtimePolicy=existing-only)` 对账角标；`subscribeSessionsIndexV4` 失败 → `listSessions` 只读拉一次列表【实证】。

## 7. sendConversationCommandV4 命令信封

**这是唯一的执行入口**：服务端把信封原样转发 CLI 的 v4/command，CLI 侧经 startPromptTurn → Core admission 进入 agent 循环【移植 zcodeAgentService.ts:5044、v4-gateway.ts:10】。移动端一切「发命令、桌面代执行」都走它。实现：`RemoteConversationStore.sendCommand`（`RemoteConversationStore.swift:1412` 起；CAS 包装 `sendCASWithRetry:2721` / `ensureStateRevision:2734`）。

### 7.1 参数形状（web 端精确形态，必须嵌套）【实证】

```json
{
  "workspacePath": "<workspace.path>",
  "workspaceIdentity": "<identity，缺失可省略>",
  "envelope": {
    "commandId": "<UUID>",
    "clientId": "<握手注册的 clientId，逐字相等>",
    "type": "<命令类型>",
    "payload": { …命令参数… },
    "issuedAt": 1759650000000,
    "sessionId": "<目标会话，无会话命令省略>",

    "baseLogEpoch": "<订阅水位 logEpoch>"

```

**逐字段纪律（全部实证）**：

| 字段 | 纪律 | 违反后果 |
|---|---|---|
| 信封形态 | 必须嵌套 `envelope:{…}`，外层扁平 `workspacePath`/`workspaceIdentity` | 平铺形态被新版服务端直接 TypeError（仅作旧版兜底重试保留） |
| `envelope.sessionId` | **键必须恒在场**：普通命令传目标会话 id；createSession 传 **null**（web `zC` 恒携带该键）【实证 2026-10-06】 | 缺省（键不存在）被拒 `proto.invalidPayload`："path:[sessionId] expected string, received undefined"——曾致移动端 createSession 全部静默失败（本地 UUID 兜底掩盖） |
| `envelope.clientId` | 必须等于握手注册值 | `fault.command.clientMismatch` |
| `envelope.issuedAt` | **epoch 毫秒数（int）** | ISO 字符串被拒 `proto.invalidPayload` |
| `envelope.baseRevision` + `envelope.baseLogEpoch` | **CAS 类命令两者必须同时在场**（baseRevision=当前会话 state `revision`；baseLogEpoch=订阅水位 logEpoch）。已确认 CAS 类：`switchModelConfig`、`pauseGoal`/`resumeGoal` | 只带其一或缺省被拒 `proto.invalidPayload`："CAS commands require baseRevision and baseLogEpoch"。revision 来源：快照/state.updated 的 `state.revision`；快照无 state 的会话先 `resyncConversationV4`（base:null）预种【实证 2026-10-05】 |

| CAS 竞态 | 命令间隙 revision 会被服务端推进（队列准入/排空等），按回填 revision 下发可能收到 `status:"stale"`、`reasonCode:proto.staleRevision`——回执自带最新 `revisionAtDecision`（sendCommand 已回填），**原样重发一次即命中**（`sendCASWithRetry` 纪律）【实证 2026-10-06 探针】 | 不重试则用户在活跃排空期的点按间歇性失败 |

## 8. 移动端边界（ReadOnlyGate）

**产品边界**：手机可以发命令、由桌面执行与修改；**手机不得直接编辑桌面/云端文件**。协议/服务端并不阻止手机发执行类命令（scope 层对 web-remote-replayable 无收窄【移植 zcodeAgentConnectionScope.ts:702-718】），因此移动端在 RPC 出口自查——`ZCodeServerConnection.call` 是**所有**调用的唯一出口，拦截记录留最近 20 条【实证】。实现：`ReadOnlyGate.swift`。

四分类：

| 分类 | 语义 | 处置 |
|---|---|---|
| readOnly | 订阅/分页查询/附件读 | 放行 |
| session | 会话元数据/账本写（置顶/归档/未读/rename/draft 转正），不驱动 agent | 放行 |
| command | 客户端发命令、桌面代执行（消息/审批/停止/队列/会话管理/workflow 控制） | 放行 |
| directWrite | 文件直写/回滚/仓库写/宿主与配置写/凭据写 | **一律拦截**（`ReadOnlyViolation`） |

**收口规则**（新增接口前必查）：

- `zcode-agent`：`sendConversationCommandV4` → 仅拦 `applyFileRewind`；其余直发命令走黑名单（`set*` 配置写、`writeWorkspaceFile/saveFile/writeFile/applyEdits` 编辑器保存、插件写 10 族（**2026-10-06 起 `installPlugin`/`uninstallPlugin` 移出黑名单放行**，见下修订）、workflow 文件写、自动化写族、`generateWorkspaceText/testModelConnectivity` 等）→ 其余默认只读。
- `zcode-task`：黑名单 `setMode/setConfigOption/setModel/setAutomationSessionConfig/restartWorkspaceProcess`；任务元数据写（setTaskPinned/archiveTask/setTaskUnread/renameTask/unarchiveTask）放行。

- **回执**：state 判别联合（strict）：`{uploadId, state:"staging", nextChunkIndex(int≥0)}` | `{uploadId, state:"committed", nextChunkIndex, ref(min1)}`——committed 直接拿 ref 短路（免分块）；staging 的 nextChunkIndex = 服务端已收块数 = **续传起点**。
- **错误与兜底**：`nextChunkIndex > totalChunks` = 事务状态不可信（移动端判 `fault.attachment.invalidServerProgress` 语义中止）。未送达 1.2s 退避重发一次（AGENTS §5.8）；失败文本回传 UI。
- **调用点**：`RemoteConversationStore.swift` attachmentBeginV4（§13 v1.12 波次后行号以代码为准）；服务编排 `AttachmentUploadService.swift`（runTransaction）。

**9.1.16.b `attachmentChunkV4`**——分块下发。
- **参数**（客户端键集 6-7 键）：`{workspacePath, workspaceIdentity?, sessionId, uploadId, chunkIndex(int≥0), dataBase64}`。**块大小 384KB**（上游 `ATTACHMENT_UPLOAD_CHUNK_BYTES=384*1024`）。每块独立 base64 **自带 padding**（AGENTS §5.7）。
- **回执**：`{uploadId, nextChunkIndex(int≥0)}`（strict）——**进度判定 = `nextChunkIndex === chunkIndex+1`**，不符即服务端进度不可信。

- **调用点**：`RemoteConversationStore.swift` attachmentChunkV4；`AttachmentUploadService.swift`。

**9.1.16.c `attachmentCommitV4`**——收口。
- **参数**（客户端键集 3-4 键）：`{workspacePath, workspaceIdentity?, sessionId, uploadId}`。

**9.1.16.d `attachmentAbortV4`**——失败路径中止（web PCe catch 分支：Begin 返回后的事务失败发 Abort；Abort 失败 warn-and-continue 不掩盖原始错误）。同 Commit 形（客户端键集 3-4 键）。
- **移动端口径**：Abort 送达 = 事务已关（重试重开新事务、uploadId 置 nil）；未送达 = 保留 uploadId 续传（断线重连场景），孤儿事务桌面超时回收；Abort 失败以 4s 短暂提示如实告知（不静默），原始错误仍在附件条 errorText 持久展示。**与 web 的有意差异**：web 每次调用一律换新 uploadId，移动端按 Begin 回报 nextChunkIndex 续传（协议内行为，策略不同，记录备查）。
- **调用点**：`RemoteConversationStore.swift` attachmentAbortV4；`AttachmentUploadService.swift`（abortTransaction）/（移除待发条）。

**替身验收**（2026-10-07）：E2E 替身服务器按 web 客户端键集严格校验四方法（多带 connectionId 记形状错误绊线），test10 全链通过（Begin→Chunk×4→Commit→sendText 携带 ref）。

#### 9.15.5 错误帧族 `app-error` / `workspace-bridge-error`（下行收口）【移植·bundle 逆向】
