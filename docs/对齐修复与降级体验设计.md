## §0 总则

### 0.1 术语与状态机基线

连接四态（`AppSession.Mode`，AppSession.swift:158-164）：

| 态 | 进入条件（实读确认） | 数据层 |
|---|---|---|
| `demo` 未配对 | bootstrap 无 savedServer（AppSession.swift:309-339） | 无任何数据（移除 Mock 后） |
| `connecting` 连接中 | ① 冷启动有 savedServer 自动重连（:333-334）；② 用户从引导页/横幅发起 | 上次快照或空 |
| `connectFailed` 连接失败 | connect 失败（:441-443，**此时 teardownRemoteStores**） | 无快照（Store 已拆空） |
| `disconnected` 断线 | 曾连接后 WS/中继中断（:257-261，**不 teardown**） | **最后快照仍在内存** |

关键事实（决定 §1 方案可行性）：断线路径不调 `teardownRemoteStores()`（该方法定义 :1057-1064，仅 connectFailed 路径 :442 与 deleteServer :955 调用）——remote Store 实例与缓存数据在断线后仍存活，「断线保留最后快照」只需装配层不再换 Mock 即可成立。

### 0.2 隐藏标记约定（全部隐藏点统一）

被隐藏的入口代码不删除，统一用单行注释标记，真机取证通过后整块恢复：

```
// HIDDEN(对齐修复): <原因一句话> · 恢复条件：<需要什么证据/接口>
```

例：`// HIDDEN(对齐修复): startSavedWorkflow 不在 web 枚举、payload 零取证 · 恢复条件：桌面真机探针 accepted`。

### 0.3 设计令牌

沿用 `docs/P1P2P3功能UI设计.md` §0.1 全部约定：`T.accent/T.orange/T.red` 色彩、`T.font/T.mono` 字体、`EmptyStateView`（Components.swift:175-215，全 App 禁骨架屏）、`CenterLoadingView`（:217-231）、3s 自动消失轻反馈 hint、`confirmationDialog` 确认层、sheet 底部 Capsule 把手 36×4。本文不重复定义，仅标注复用点。

### 0.4 空实现 Store（移除 Mock 的编译基座）

- `StoreEnvironment.swift:8-12` 三条 `@Entry` 默认值现为 Mock 实例，`ZCodeMobileApp.swift:10-12` 三个 `@State` 初值同为 Mock——**移除 Mock 后这两处必须换空实现**，否则编译断（调研 patterns 实证全仓 `@Environment(\.xStore)` 消费面波及）。
- 新增三个轻量空实现（建议名 `EmptyConversationStore/EmptyTaskStore/EmptyFileStore`，单文件）：全部读方法返回空、观察流返回立即结束的 `AsyncStream`；`isReadOnly` 按语义取值——`EmptyConversationStore.isReadOnly = false`（ChatView 以 `viewModel.isReadOnly` 区分连接态 chips/模式行，未连接态走本地 `toolsRow` 分支 ChatView.swift:881-885，行为正确）；**写路径必须返回失败**——协议默认实现 `sendWithAttachments`（StoreProtocols.swift:321-327）转发 `await send(...)` 的返回值，故 Empty store **覆写 `send()` 返回 `false`** 即可令转发链为 false（不必覆写 sendWithAttachments）；`createConversation` 不返回成功占位（未连接态新建入口已按 §2 H13 隐藏，该方法正式路径不可达，此处为防御性兜底，防 onCreated → openChat 假成功导航）。
- `StoreProtocols.swift` 三处 extension 默认实现（:215 起 / :431 起 / :499 起）**不动**：远端实现不逐项覆写（如 `FileStore.contentPage`），且 ConversationStore 本体 requirement 声明承担 any 动态分派约束（:30-36 注释）。

## §1 设计点 1：未连接态整体改造（四态呈现）

### 1.1 目标与总体方案

未配对 = 连接引导页为根（整层替换，U-1 推荐方案）；连接中 = Tab 骨架 + 全局连接中横幅（**唯一呈现缺口，新增**）；断线 = 保留最后快照 + 橙横幅；连接失败 = 空态 + 红横幅。四态均**不出现任何 Mock 数据**。

### 1.2 入口与插入点

| 动作 | 位置 | 现状（实读） |

**根页场景适配（三处差异）**：
- 不渲染 `ConnectFlowView.swift:37-50` 的 ✕ 关闭钮（那是 cover 场景控件；根页无处可关）。实现上建议给 ConnectHomeView 加 `isRoot: Bool = false` 参数，root 模式下由外层不包 toolbar 即可，或直接在 RootView 内嵌 `ConnectHomeView(onScan:…onManual:…)` 并自行挂 NavigationStack（manual/help 两目的地照抄 :26-33）。

- **连接中整层反馈**：根页发起连接（扫码/手动/一键填充 → `ConnectHomeView.connect(config:)` ConnectFlowView.swift:318-321 → `session.connect(server:)` AppSession.swift:934-937，**不置 presentedFlow**）后 mode 转 connecting——按 §1.2 根页替换条件（connecting 且从未连上）根页**继续在场**，overlay 整层 `ConnectingView(onCancel:)`（复用 ConnectFlowView.swift:56-60 同件），与 cover 场景（`presentedFlow` 非 nil，由 `requestConnectFlow` AppSession.swift:201-203 置位）的反馈量级一致。这样取舍：两条路径的「连接中」都是整层遮蔽（发起动作的上下文还在眼前），差异只在失败层归属（见状态表）；断线重连的连接中则用细横幅（1.4），不打断快照浏览。

**全部状态**：
| 子态 | 呈现 |
|---|---|
| 剪贴板无链接、无 savedServer | 品牌区 + 扫码 + 手动 + 帮助（最简首启） |
| 剪贴板有链接 | 顶部多出横幅，「一键填充」直接发起连接 → 根页叠加整层 ConnectingView（本节第三条差异） |
| 用户已登录 OAuth 未配对 | 不影响本页（账户入口在设置页；根页不提供设置入口——未配对无可配置的远控内容，属可接受取舍；外观/语言设置经连接后可达） |
| 根页发起后失败 | mode→connectFailed 且 presentedFlow 为 nil（根页发起不置位）→ 根页替换条件不再成立、整层消失 → **四 Tab 空态 + 红横幅（1.6）；ConnectFlowView 的 L3 失败层（ConnectFlowView.swift:61-75）在根页场景不在场**——重试走红横幅动作 |
| cover 场发起后失败 | presentedFlow 非 nil（设置页「添加服务器」SettingsView.swift:106-116、空态 CTA、登录后等经 `requestConnectFlow` 触发）→ ConnectFlowView cover 在场，overlay L3 失败层（:61-75）照常呈现 |

### 1.4 连接中：全局连接中横幅（新增，覆盖断线重连场景）

现状 connecting 态挂 Mock UI（可操作假数据）；`ConnectingView` 仅在 ConnectFlowView overlay（ConnectFlowView.swift:56-60）可见，**冷启动自动重连（无 presentedFlow）时无任何专门视图**（调研补充节实证）。

**适用范围（与 1.3 分工）**：横幅只覆盖「connecting 且曾有连接」——即断线后自动/手动重连（`session.remoteConversationStore != nil`，快照在场，不打断浏览）；从未连上的 connecting（冷启动无凭据不算、根页/cover 发起）由整层 ConnectingView 承担（1.3），横幅不重复出现。

**方案**：`RootView.connectionBanner` 新增 `connecting` 分支，复用 `ConnectionBanner` 组件（RootView.swift:172-218，弱底+描边+图标+动作文）：

- 图标：`ProgressView` 小 spinner 或 `arrow.triangle.2.circlepath`（建议 spinner 13pt，与 ConnectingView 呼应）；tint `T.accent`
- title：`正在连接桌面端…`
- detail：server.displayName + displayAddress（mono 10.5）
- action 文案：`取消`，动作见下方「取消落态」
- 底层保留四 Tab + 最后快照——连接中**不锁页面**，用户可浏览快照/本地设置
- a11y identifier：`13-banner-connecting`——注意 `ConnectionBanner` 现硬编码统一 `13-banner-connection`（RootView.swift:211）且 `Model` 六字段不含 identifier：**组件需小改**——Model 增第 7 字段 `var identifier: String = "13-banner-connection"`（默认值令既有三态与全部 E2E 断言不变），connecting 分支传 `13-banner-connecting`

**取消落态（关键设计约束，防违反 1.5 裁决）**：`session.cancelConnecting()`（AppSession.swift:939-942）现无条件 `mode = .demo`——若断线重连中取消，mode 落 demo 后 §1.2 装配策略会把 store 换 Empty*Store + 根页接管，**快照丢失、回落引导页**，恰是「断线保留最后快照，不回落引导页」要防的结果（连接层已有 manuallyCancelled 守卫防把取消误报为 connectFailed，问题纯在 mode 落态；评审核实）。**落态规则改为按场景分流**（AppSession.swift:939-942 一处小改）：

| 取消时场景 | 判定 | 落态 | 呈现 |
|---|---|---|---|
| 从未连上（根页/cover 发起的连接中取消） | `remoteConversationStore == nil` | `.demo`（不变） | 回根页引导（正确归宿：无数据可保留） |
| 断线重连中取消 | `remoteConversationStore != nil` | `.disconnected(server, "已取消重连")`（新增分支） | 快照保留 + 1.5 橙横幅（detail 显示「已取消重连」），用户可随时再点「重连」 |

### 1.5 断线态：保留最后快照

**裁决：断线保留最后快照，不回落引导页**。依据：数据层天然支持（§0.1）；用户在地铁/电梯场景回看消息与任务列表是真实诉求；写面全部不可用（连接已断），由 §5 错误提示兜住。

- **横幅**（RootView.swift:135-142 既有组件，改文案）：icon `wifi.exclamationmark`、tint `T.orange`、title **`已断开 · 显示断线前的数据`**、detail 原 detail（断线原因）、action `重连` → `session.reconnect()`（不变）
- **页面**：四 Tab 正常浏览快照；用量/权益等只读信息在断线瞬间**不主动清空**（`onConnectionDropped` AppSession.swift:257-261 仅切 mode；`refreshDesktopReadonlyInfo` 的 `guard connection.isActive` 清空是懒的——调用点在各视图触发刷新时，如设置页 `.task` SettingsView.swift:263-269）。即断线快照期设置页用户卡可能仍显示旧额度，待下次进入/触发刷新才清——属「快照」语义的一部分，如实保留；连接恢复后被新数据整体替换
- **写操作**：composer 发送→「未送达」+草稿保留（§5）；审批→「审批未送达」（§5）；队列/模式切换等 CAS 命令同理（controlFeedback 已有失败口径）
- **重连成功**：mode→connected，storeEpoch 经 assemble +1（AppSession.swift:1054），环境值换绑新 Store 重拉——快照被新数据整体替换，无合并歧义
- **重连失败**：connectFailed → teardown（快照被清）→ 空态 + 红横幅（1.6）。此落差如实（重连失败=数据源确认不可用），不做过渡动画掩盖

## §3 设计点 3：审批 Sheet 的 optionId 化（改传参，不隐藏）

### 3.1 wire 形态基线（web 实证，审查报告 A-3）

`resolveInteraction` 的 `answer` 恒为对象，按交互族分形：

| 族 | answer 形态 | 值域 |
|---|---|---|
| 权限审批 | `{optionId}` | 按钮即选项：`allowOnce` / `allowAlways` / `rejectOnce` / `rejectAlways`（+ 服务端 options 可携其它【宽容】） |

### 3.2 权限族：任务审批 Sheet（ApprovalSheetView）与会话内审批卡（ApprovalInteractionCard）统一改造

**入口与插入点**：
- 任务页 Sheet：`ApprovalSheetView.swift`——AuthScope 枚举 :12-36、scope state :38、scopeSection 三档卡片单选 :149-192、actionBar :207-242、dismissAfterDecision :307-310；呼出点 TaskBoardView.swift:232-234
- 会话内卡：`ChatView.swift` `ApprovalInteractionCard`——AuthScope :367-384、chips :434-450、两钮 :451-475、decide :525-532；挂载点 ChatView.swift:90-101（composer 上方常驻）

**optionId 推导规则（两处同一规则，工程师照抄即可）**：

1. **投影扩展**（前置工程项）：`parseInteraction`（RemoteConversationStore.swift:1691-1692）现把 options 投影为纯 label 字符串数组——改为保留 `(id, label)` 对（元素为对象时 id=`id`/`optionId` 键、label=`label`/`title` 键；元素为裸字符串时 id=label=该串）。`RemotePendingInteraction.options` 类型同步（Models.swift:240-255）。
2. **默认（options 空）**：范围 chips 两档——`仅本次`（once）/`始终允许`（always，「需谨慎」红字提示保留）；批准/拒绝两钮不变。点按时拼 `optionId = (approved ? "allow" : "reject") + (scope == .always ? "Always" : "Once")`。
3. **options 含四族（含部分命中的混合态）**：chips 可见性与**组合有效性**都按四族命中推导——
   - chip「仅本次」渲染 ⇔ `allowOnce` 或 `rejectOnce` 至少一个在场；chip「始终允许」渲染 ⇔ `allowAlways` 或 `rejectAlways` 至少一个在场；默认选中第一个两方向齐全的档（无齐全档则选首个可见档）。
   - **方向钮禁用规则（混合态核心）**：选中某 scope 时，方向钮仅当对应四族项在场才可点——如 options=`[allowOnce, rejectOnce, rejectAlways]`：「始终允许」chip 可见（rejectAlways 命中）但选中它时**「批准执行」钮禁用**（allowAlways 不在词表，拼出即词表外 optionId），「拒绝」钮可点；切回「仅本次」两钮均恢复。禁用态 = 既有视觉语言（`T.text3.opacity(0.5)` + 不可点，先例 disabledChip NewConversationSheet.swift:319-329），钮旁不加额外说明（chip×钮的可用性自解释）。
   - **options 全为非四族 id**：两步交互整体退化为**单选即决**——chips 即选项（点选即发 `{optionId: 该 id}`，自带方向语义，不再拼接），批准/拒绝两钮整组隐藏；此时 Sheet 布局中 actionBar 区被 chips 行替代，退出动作（追问/稍后）保留。
4. **「本任务内」档删除**：现三档中的 task 档在 wire 四族值域中无对应（web 无此枚举），默认矩阵中移除；仅当服务端 options 明确携带等效非四族 id 时按规则 3 末条呈现（作为直选 chip，不进两步矩阵）。

## §4 设计点 4：投递模式三档语义（now 档不下发命令）

### 4.1 语义修正（A-2）

web `setFollowupMode` 枚举仅 `queue | guide`；「立即」不是 followupMode 值——web 默认 followupMode=`queue`，立即语义由逐消息 `requestedDelivery:"startNow"`（sendText 可选参数）承载。修正后：

- **now 档**：**不下发 setFollowupMode**，仅本地落态 + 持久化（ComposerModeStore）；本条及后续消息的投递按「立即」处理
- **queue / guide 档**：照常 CAS 下发（ensureStateRevision + sendCASWithRetry，AGENTS §5），成功才落态
- sendText 的 `requestedDelivery`（ChatViewModel.swift:142-144 `requestedDeliveryKey`）：**定为唯一方案——now 档恒携 `requestedDelivery:"startNow"`**（web 立即语义的实证形态，审查报告 A-2 引 sendText schema）。排除「不带键」备选的理由（评审纠偏）：web 默认 followupMode=queue，且本设计 queue 档会 CAS 把桌面置 queue——此后切回 now 不下发命令，若消息不带键则桌面仍按 queue 处理、回合进行中即排队，「立即发送」呈现失真；不带键仅在桌面从未被置 queue 时行为正确，存在矛盾窗口，故不成立。探针裁决点保留：`startNow` 首击回执（若真机被拒，退路是回退档位文案并暂停 now 档菜单项，而非静默不带键）。

## §5 设计点 5：发送/审批失败的错误提示与草稿恢复

### 5.1 发送失败静默丢稿（U-6，数据丢失类）

**现状链（实读）**：`ChatViewModel.send()`（:665-677）draft 先清空（:673）→ `RemoteConversationStore.sendWithAttachments`（:1360-1389）ack==nil 时撤销乐观回显（:1379-1388）→ `ChatView.sendAndHintDelivery`（:1363-1370）忽略 false，消息凭空消失、草稿丢失。

**改造呈现**（三件套，挂 composer 内）：

1. **draft 回填**：send() 失败（返回 false）时把文本写回 `viewModel.draft`（仅当用户尚未重新输入——以失败时刻 draft 是否为空判断，避免覆盖新输入）；焦点回到输入框（`inputFocused = true`）。
2. **持久错误行**（非 3s 自动消失）：插在 switchHint 行同位置（ComposerBar.body ChatView.swift:857-863 的 else-if 链**之前**，错误优先级高于轻提示）：

```
│ ⚠ 消息未送达 · 已恢复草稿            [重试]  │
│   ← exclamationmark.circle.fill T.red 12pt +   │
│     T.font(12) 文案 + 重试钮（T.red 44pt 热区） │
```

- a11y id：`05-composer-send-fail`；出现时触觉 `UINotificationFeedbackGenerator().notificationOccurred(.error)`
- 「重试」→ 重新 `send()`（携回填后的 draft）：成功→错误行清除 + 走正常投递提示；再失败→行保留
- 清除时机：发送成功 / 用户手动编辑 draft / 离开会话——**不**随 3s 定时消失（数据安全提示必须显式关闭）
3. **断线子文案**：失败且 `session` 非 connected 时文案换 `消息未送达 · 连接已断开，草稿已保留`（重试钮保留，重试会在连接恢复后可用）。

**状态矩阵**：
| 状态 | 呈现 |
|---|---|
| 发送成功 | 无行；乐观回显由服务端行替换（既有） |
| 发送失败（拒收） | 错误行 + 草稿回填 + 焦点回输入框 |
| 发送失败（断线） | 断线子文案行 + 草稿回填 |
| 重试中 | 行内文案换「重试中…」，重试钮 disabled |
| 附件发送联动 | `uploads.firstFailureText` 通道（:874-880）不变；两行同时在场时发送错误行在上 |

**连带（工程口径）**：`Empty*Store.sendWithAttachments` 返回 false（§0.4）——未连接态（connectFailed 空态/未配对）不可达会话页，disconnected 快照态可达且可点发送，由本设计兜底。

### 5.2 审批假成功（U-5）

**现状链（实读）**：`RemoteTaskStore.resolvePermission`（:193-207）interaction 不在场时静默 return；`ApprovalSheetView`（:209-237）await 后无条件「已批准执行/已拒绝」+ dismissAfterDecision。

**改造呈现**：approve/reject 返回结果（三态：accepted / interactionId 不在场 / 回执拒绝或未送达——协议签名随 §3.5 optionId 形参一并改），Sheet 按 §3.2 状态矩阵末四行呈现：

- 成功：toast `已批准执行 · \(范围label)`（比现状多范围回显，与所点 chips 闭环）+ 0.7s dismiss（:307-310 保留）
- 交互不在场：toast `未找到待审批交互 · 可能已在桌面端处理`（accentDim 底样式复用 decisionToastRow :194-204），**不 dismiss**，同时后台刷新任务状态（task(id:) 刷新链 SettingsView.swift:263-268 同款口径）
- 拒绝/未送达：toast `审批未送达 · 连接恢复后再试` / `桌面端拒绝（reasonCode）`，按钮恢复可点

会话内两卡（Approval/Plan/Question）失败态见 §3.2-3.4 状态矩阵（卡内错误行，卡片不撤）。

### 5.3 设计语言一致性

- 错误行复用 composer 既有「一行横排提示」范式（switchHint/attach-hint 同区位同字号 10.5-12pt），仅色值升为 T.red、增加动作钮与持久语义——「轻提示 3s / 错误持久」的双轨与 spec 5.9 错误 UI 口径一致

- 草稿回填不弹 alert（不打断输入流，就地恢复 + 可见说明即可）；「重试」为 44pt 热区文字钮（T.red，与「拒绝」钮色语言同源）
