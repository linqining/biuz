# UI 还原与测量判定（ui-parity）

> 解决两个问题：① web 的 CSS 数值**怎么换算**成 App 的布局值；② 换算后的结果
> **达不达标怎么判**（可机检，不靠目测感觉）。

## 1. 读 web 数值前先判适配栈（不做这步直接换算 = 全错）

web 项目的 CSS 值很少是"设备像素"，先从源码摸清三层：

1. **设计稿基准**：tailwind/uni-app 类框架的 `tw-*`/样式原子值通常是**设计稿 px**
   （常见 375 或 750 基准），不是运行时像素。
2. **缩放机制**：找根字号/缩放变量的设定代码——`--unit`/`--rootValue`/rem 基准/
   `getCalcCSSValue` 一类的换算函数。典型双层机制：**设计稿 px ÷ 基准宽 → frame
   比例 × 运行时根字号**。只做一层换算会差一整倍。
3. **钉死帧与双份数字**：有的页面钉死宽度不响应（换算按钉死帧）；横竖屏各自一套数字
   的，两套都要采。

判定方法：在 devtools 里改窗口宽度，看目标元素的 computed px 是否变化——
变的走比例换算，不变的按绝对值；再用 2~3 个元素反推验证换算式。
**禁止把样式值直接除以屏幕宽**；禁止对钉死件"顺手响应式"。

换算的目标单位按平台：iOS **pt** / Android **dp** / 微信小程序 **rpx（750 基准，
`rpx = web 采证视口内 px × 750 ÷ 采证视口宽`）**；先换到目标单位再实做，
不要"写完再目测调"。

## 2. 网格比例测量法（可比对的判定语言）

对齐的判定统一用**归一化四元组**：以采证视口（如 390×844）为分母，
元素位置尺寸表达为 `[x%, y%, w%, h%]`。

- web 侧：截图 + DOM `getBoundingClientRect()`（采证时的 `dom.html`/eval_js 均可）
- App 侧：**读目标元素本身**的 bounds（`uiautomator dump` 的节点 bounds /
  `XCUIElement.frame` / Compose `onGloballyPositioned`），不靠「截图上目测量取」
- 判定：逐元素比较，`|差值|` 进容差表

**目标元素 = 用户看到的那一层，不是它的容器**：画布居中 ≠ 机身满宽，父容器满宽 ≠ 子元素满宽。
每条布局结论必须能写成 `target / expected / measured / tolerance` 五项，口径与反例见
`layout-claim-evidence.md`——没有目标元素 bounds 的「满宽 / 居中 / 无黑带 / 被裁」一律记为
`unverified`，不得写成 `pass`。

容差基线（可按项目在文档中收紧/放宽）：

| 项 | 容差 |
|---|---|
| 尺寸（w/h%） | ±0.5% |
| 间距/位置（x/y%） | ±0.75% |
| 字号 | 换算后 ±0.5px |
| 颜色 | 色值逐字一致（同一 token） |
| **触控命中区** | **物理 ≥48dp（iOS ≥44pt），零容差** |

### 2.1 有缩放层时，容差要乘 s（2026-11-24 实证回写）

若端上存在「根容器等比缩放」（`s = clamp(视口宽/设计基准, 下限, 上限)`，见
`source-to-contract.md` §2.9 M17），则**所有尺寸期望值必须乘 s 再比**：

```
|measured − expected × s| ≤ 2%
```

理由（mtt_mobile 实测）：360dp 视口 `s = 360/390 = 0.9231`。若用固定「≤5% 不算缺陷」，
7.7% 的整体缩小会被判成缺陷；反过来若某子层又乘了一次 `390/375`，累计可达 10%，
固定阈值反而可能放行。**先记 s，再按 s 判**。

两条附加断言（缺一即不可判 pass）：

1. **基准视口零变化**：`s=1`（等于设计基准宽）时逐像素不变——这是证明「只乘一次」的正控；
2. **触控单独测**：`min(命中区宽,高) × s ≥ 48dp`，不达标即 FAIL。视觉等比缩小是**正确**的
   （web rem 语义），但命中区跟着缩是**缺陷**（32dp 钮在 360 屏只剩 29.5dp）。

**六类判定**（每个元素必须落进一类，不许"差不多"）：

1. 一致（容差内）
2. 容差外偏差（缺陷，入 BACKLOG）
3. 刻意差异（有差异标记编号）
4. web 侧 bug/兜底态（App 侧不跟，记差异标记 `business`）
5. 平台语义不同（安全区/IME/返回，走平台封装，记 `platform`）
6. 不可比（canvas/引擎层内容，按截图帧互证）

rem 整页等比语义：整页按同一根字号等比缩放的，比例四元组天然一致；
发现整页系统性漂移先查根字号换算，不要逐元素修。

## 3. 资源与字体

- 图片/图标**同源下载**（采证时的 URL 逐字对齐），不做近似重绘、不拿截图裁剪充当。
- 字体：web 用的字体族 App 侧要么打包同字体，要么确认识别回退并记差异标记；
  验收截图里出现明显 fallback 字体/缺字 = P2。
- canvas/引擎层不适用网格法（渲染内容不在 DOM），以截图帧互证 + 素材 URL 同源为主。

## 3.5 字体与截断：用真实度量，不用码点

排版与截断最容易「看起来对、实际错」，因为错法只在极端样本上显形：

- **宽度测量**：用平台真实文本测量（Compose `TextMeasurer`/`rememberTextMeasurer`、
  Android `Paint.measureText`、iOS `NSAttributedString.size()` / `CTLine`），
  **禁止**「字符数 × 平均字宽」或手调宽度表——中英混排、emoji、组合字形、窄体字全错。
- **截断**：按**字素簇**（grapheme cluster：Swift `Character`、Kotlin `BreakIterator`
  或 ICU segmenter）二分查找，**省略号计入宽度预算**；按码点切会把 emoji/组合字撕成半个。
- **预算派生**：maxWidth 与容器尺寸从 web **同比例**派生（不要手抄像素），省略号宽度、
  内边距一并计入。
- **必测样本**：超长昵称 / 长文件名 / 长 URL 混 CJK / emoji 结尾 各一条，
  三端都不得冲出容器、不得把容器撑变形。
- 验收判定：给「必然溢出」样本时若容器被撑开或文本溢出边框 = P1；截断位置不同但都在容器内 = P3。

## 4. 文案对等

- 文案**逐字一致**（含尾空格、全半角、占位符顺序）——拼接字面量先拼完再比。
- i18n 项目先确认**权威语言包来源**：远端语言包快照才是权威；仓库内兜底语言文件
  **缺键 ≠ web 无文案**（可能是按需加载/远端合并）。裁决"缺 key/裸键直出"类问题
  前必须对权威源，不要用兜底文件下结论。
- 动态文案（金额/时间）：格式化规则进逻辑对拍（`logic-parity.md`），不进目测。

## 5. 缺陷优先级口径

- **P1** = 结构缺失/错误布局（用户可见硬伤：缺块、层级错、金额类错误）
- **P2** = 元素缺失/样式偏差（素材错、字体回退、超容差）
- **P3** = 文案/角落细节
- 金额类与交互阻断类一律最高优。
